# Security — защищённый мессенджер

Веб-мессенджер со сквозным шифрованием, звонками, файлами и голосовыми сообщениями.
Клиент и сервер написаны на чистом JavaScript: **ни одной внешней зависимости**, запуск — одна команда.

```
  ██  Security
  ▸  E2E-шифрование · звонки · файлы · голосовые
```

---

## Быстрый старт

```bash
cd security-messenger
node server.js
```

Откройте **http://localhost:3000**.

### Бета-режим и код доступа

По умолчанию включён `betaMode: true`: после ввода номера телефона или Gmail 6-значный код
входа появляется **прямо на экране**. Никакие SMS и письма при этом не отправляются.

При первом входе создаётся **постоянный код доступа** — 8 символов вида `XXXX-XXXX`.
Он показывается один раз, а затем хранится в зашифрованной базе и доступен в
**профиле → «Безопасность»**. При следующем входе на тот же номер или адрес после
кода подтверждения потребуется ввести этот код доступа.

> Бета-режим — осознанное ослабление безопасности: любой, кто знает номер или адрес,
> может получить код входа на экране. Код доступа защищает только повторный вход,
> а не первую регистрацию. Не используйте бета-режим для настоящих секретов.

Чтобы вернуть отправку кода на Gmail, укажите SMTP-данные и выключите бета-режим:

```json
{
  "appName": "Security",
  "authMode": "both",
  "betaMode": false
}
```

`authMode` задаёт разрешённые способы входа: `both` (телефон или Gmail), `sms` (только телефон),
`email` (только Gmail). Без бета-режима телефонный вход отключён — используйте Gmail.

### Настройка Gmail (код письмом)

Это **не** вход через Google OAuth: приложение отправляет письмо с кодом через Gmail SMTP.
Нужен обычный Gmail-аккаунт и **пароль приложения** Google (16 символов).

1. Включите двухэтапную аутентификацию: https://myaccount.google.com/security
2. Создайте пароль приложения: https://myaccount.google.com/apppasswords
3. Заполните `security.config.json`:

```json
{
  "appName": "Security",
  "authMode": "both",
  "betaMode": false,
  "smtpHost": "smtp.gmail.com",
  "smtpPort": 465,
  "smtpUser": "ваш.адрес@gmail.com",
  "smtpPass": "пароль_приложения_16_символов",
  "smtpFromName": "Security"
}
```

4. Перезапустите сервер.

`authMode: "both"` разрешает и телефон, и Gmail (телефон — только в бета-режиме).
Аккаунты Gmail и телефона — разные: при первом входе по e-mail создаётся отдельный
пользователь, безопасность телефонных аккаунтов не меняется. Письмо уходит на любой
адрес, не обязательно Gmail.

> Если пароль приложения не подходит, Gmail вернёт ошибку авторизации — она будет
> в консоли сервера. Код при этом не сохраняется и в ответе API не появляется.

### Сборка .exe

```bash
npm install
npm run build:exe
```

Готовый файл: `dist/security.exe`. Рядом должны лежать `security.config.json` и `data/`.
Подробности в `release/README-РЕЛИЗ.txt`.

> Важно: камера и микрофон работают только в **безопасном контексте** — `http://localhost`
> или HTTPS. По локальной сети по `http://192.168.x.x` браузер заблокирует звонки.

### Как проверить переписку вдвоём

Локальное хранилище браузера привязано к origin, поэтому два аккаунта в одном профиле
одновременно не уживутся. Варианты:

1. Открыть `http://localhost:3000` и `http://127.0.0.1:3000` — это разные origin, у каждого свой аккаунт.
2. Открыть второе окно в режиме инкогнито.
3. Запустить второй сервер на другом порту (`PORT=3001 node server.js`) — но тогда у аккаунтов будет разная база.

Второй пользователь должен хотя бы раз войти, чтобы у него появился ключ шифрования.
Затем в первом аккаунте: **+ → номер собеседника → Найти → Написать**.

## Что умеет

- **Авторизация по телефону или Gmail** — 6-значный код на экране (бета) либо письмом, ограничение попыток, срок жизни 5 минут.
- **Постоянный код доступа** — 8 символов, обязателен при повторном входе; хранится в профиле → «Безопасность», можно скопировать или сменить.
- **Сквозное шифрование сообщений** — сервер хранит только зашифрованные конверты.
- **Текстовые сообщения** — ссылки, переносы строк, статусы «отправлено / прочитано», счётчики непрочитанного.
- **Файлы** — до 25 МБ, шифруются в браузере до отправки, скачиваются и расшифровываются на устройстве.
- **Голосовые сообщения** — запись через `MediaRecorder`, шифрование, волна и воспроизведение в чате.
- **Аудио- и видеозвонки** — WebRTC, сигнализация через SSE; кнопки «микрофон», «камера», таймер.
- **Присутствие, «печатает…», история с подгрузкой**, поиск по чатам, профиль с изменяемым именем.
- **Код безопасности** — отпечаток пары ключей для сверки голосом (защита от подмены ключа).
- Адаптивная вёрстка (десктоп и мобильный), тёмная тема.

## Шифрование: Security Cipher v1

Используются только стандартные примитивы WebCrypto.

1. При первом входе устройство генерирует долговременную пару **ECDH P-256**.
   Приватный ключ импортируется как **неизвлекаемый** и хранится в IndexedDB; на сервер уходит только публичный.
2. Для каждого сообщения генерируется одноразовая пара ECDH (ECIES):
   `ECDH(ephemeral, получатель)` → **HKDF-SHA256** → **AES-256-GCM**.
   Соль и IV — случайные для каждого конверта, открытый эфемерный ключ едет вместе с сообщением.
   Компрометация одного сообщения не раскрывает остальные.
3. Каждое сообщение шифруется **дважды**: для собеседника и для себя.
   Второй конверт позволяет читать собственную историю после перезагрузки страницы.
4. Файлы и голосовые шифруются случайным ключом **AES-256-GCM**; этот ключ передаётся
   только внутри зашифрованного конверта сообщения. Сервер видит лишь набор байтов.
5. «Код безопасности» в карточке чата — SHA-256 от пары публичных ключей, разложенный на группы цифр.

Приватные ключи не покидают браузер: их нет ни в API, ни в базе сервера.

### Что сервер всё-таки видит

Сквозное шифрование защищает **содержимое**, но не метаданные:

- номера телефонов и имена;
- кто, кому и когда писал, размеры файлов и тип сообщения (`text` / `file` / `voice`);
- факт входа и IP-адрес.

Это нормально для прототипа и описано честно, чтобы не создавать ложного чувства защиты.

## Архитектура

```
security-messenger/
├─ server.js              HTTP-сервер, точка входа
├─ security.config.json   настройки (бета-режим, SMTP, имя приложения) — необязателен
├─ server/
│  ├─ app.js              API, авторизация, коды доступа, статика, отправка email
│  ├─ store.js            JSON-хранилище с AES-256-GCM и атомарной записью
│  ├─ paths.js            пути для обычного запуска и .exe
│  └─ realtime.js         доставка событий через Server-Sent Events
├─ public/
│  ├─ index.html          разметка и SVG-иконки
│  ├─ styles.css          оформление
│  └─ js/
│     ├─ app.js           состояние, чаты, сообщения, файлы, голосовые
│     ├─ calls.js         WebRTC: offer/answer, ICE, микрофон и камера
│     ├─ crypto.js        Security Cipher v1
│     ├─ api.js           тонкий клиент REST
│     ├─ idb.js           IndexedDB для ключей
│     └─ ui.js            аватары, тосты, модалки, форматирование
├─ dist/security.exe      собранный релиз (npm run build:exe)
└─ data/                  создаётся автоматически
   ├─ db.key              ключ шифрования базы (беречь!)
   ├─ db.json             зашифрованная база (AES-256-GCM)
   ├─ files/              зашифрованные вложения
   └─ avatars/            аватарки профилей
```

- **Транспорт:** REST + `EventSource` (SSE). SSE выбран вместо WebSocket, чтобы серверу
  не требовались зависимости: доставка мгновенная, переподключение встроено в браузер.
- **Хранилище:** JSON-файл с дебаунсом и атомарной заменой, содержимое шифруется
  AES-256-GCM. Ключ — `DB_ENCRYPTION_KEY` или автоматически созданный `data/db.key`.
  Без ключа `db.json` не читается. Для больших нагрузок стоит заменить на Postgres.
- **Звонки:** `RTCPeerConnection`, публичные STUN-серверы Google, сигнализация через
  `/api/calls/signal`. TURN-сервера нет: за симметричным NAT звонок может не установиться.

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/auth/start` | запросить 6-значный код входа |
| POST | `/api/auth/verify` | подтвердить код; вернуть токен или запросить код доступа |
| POST | `/api/auth/access` | подтвердить постоянный код доступа |
| GET | `/api/me/security` | получить код доступа |
| POST | `/api/me/access-code/rotate` | сменить код доступа |
| GET | `/api/me` | текущий пользователь |
| PUT | `/api/me/keys` | опубликовать публичный ключ |
| GET | `/api/contacts/lookup?phone=` | найти человека по номеру |
| GET / POST | `/api/chats` | список чатов / создать чат |
| GET / POST | `/api/chats/:id/messages` | история / отправить сообщение |
| POST | `/api/chats/:id/read` | отметить прочитанным |
| POST | `/api/chats/:id/typing` | индикатор набора |
| POST / GET | `/api/files` · `/api/files/:id` | загрузка / скачивание шифрованного файла |
| POST | `/api/calls/signal` | сигнализация звонка |
| GET | `/api/events?token=` | поток событий (SSE) |

## Настройки

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `PORT` | `3000` | порт сервера |
| `HOST` | `0.0.0.0` | интерфейс |
| `DATA_DIR` | `./data` | каталог базы, файлов и аватарок |
| `DB_ENCRYPTION_KEY` | — | ключ шифрования базы (base64, 32 байта). Если не задан — создаётся `data/db.key` |
| `AUTH_MODE` | `both` | `both` / `sms` / `email` |
| `BETA_MODE` | `true` | показывать код входа на экране вместо отправки |
| `APP_NAME` | `Security` | название приложения в заголовке и на экране входа |
| `SMTP_HOST` | `smtp.gmail.com` | SMTP-сервер для писем с кодом |
| `SMTP_PORT` | `465` | порт SMTP (неявный TLS) |
| `SMTP_USER` | — | адрес Gmail, с которого уходит письмо |
| `SMTP_PASS` | — | пароль приложения Google (16 символов) |
| `SMTP_FROM_NAME` | `APP_NAME` | имя отправителя в письме |

Сбросить всё: остановить сервер и удалить каталог `data/`.

## Ограничения и что дальше

Это рабочий прототип, а не аудированный мессенджер. Честный список:

- **Бета-режим показывает код входа на экране.** Это удобно для демонстрации, но любой, кто знает номер или адрес, может войти. Для реального использования выключите `betaMode` и настройте Gmail SMTP (нужен пароль приложения Google, это не OAuth).
- **Нет TURN.** Звонки между разными сетями могут не пройти; нужен TURN (coturn) в `public/js/calls.js`.
- **Медиа звонков не имеет E2E-шифрования на уровне приложения** — используется встроенный DTLS-SRTP WebRTC.
  Для полной схемы нужны Insertable Streams / SFrame.
- **Один аккаунт — одно устройство.** Ключ хранится в конкретном браузере; на новом устройстве
  старые сообщения не расшифруются. Мультидевайс требует протокола вроде Signal.
- **Нет групп, реакций, ответов, удаления сообщений.**
- **Метаданные не скрываются** (см. выше), сервер доверенный в части выдачи ключей.
- **Токен SSE передаётся в query-параметре** — ограничение `EventSource`; для продакшена
  лучше WebSocket с токеном в заголовке или HttpOnly-cookie.
- **JSON-хранилище** рассчитано на небольшой круг пользователей.
- **Ключ базы (`data/db.key`) лежит рядом с базой.** Это защищает от копирования `db.json`,
  но не от полного доступа к диску. Для строгой модели задайте `DB_ENCRYPTION_KEY` вне диска.
- Перед продакшеном: HTTPS, ротация сессий, лимиты запросов, TURN, аудит протокола, бэкапы с ключом.
